# M3：多组件 start / stop

M3 实现 `ProjectAdapter.start` / `stop`：按已确认的 `run-plan.yaml` 安装、按 `depends_on` 与 `start_order` 启动**每一个**已声明组件，并分别做 healthcheck。  
它**不是** Discovery / Agent，也不是对任意 GitHub 仓库的安全执行器。

> CI 使用两个微型本地 HTTP 进程，**不**克隆真实产品仓库。  
> 产品级 Rocket.Chat 启动是**后续**在操作者 Linux 机器上、用户将该仓库标为 trusted 之后的可信运行，**不是 CI**。  
> 本里程碑**不**宣传、也**不**提供对未信任目标的“安全执行”。

## 范围内

- `ProjectAdapter.start(workspace, plan) -> StartResult`
  - `status`: `success` | `partial` | `failed-runtime`（不增加第四种 status）
  - `project`: 仅当 `status === success` 时存在，且 `usable_for_explore: true`
  - `components`: 每个已声明组件一条 `ComponentStartResult`
  - `gaps`: 拒绝或失败原因
- 只读取人类确认的 `run-plan.yaml`（`assertPlanConfirmed`）。draft → `failed-runtime`，`gap.reason = plan_not_confirmed`，不启动进程，不返回 `RunningProject`。
- phase-1 信任门：run context / trust 记录必须标明用户确认 trusted。未信任 → 不安装、不执行目标脚本，组件与 gap 说明 `refused-untrusted`。
- 解析 `depends_on`，安装各组件，按 `start_order` 启动，**每个**组件自己的 healthcheck。
- 日志写在 `runs/<run-id>/logs/`。一个健康 URL 不能证明其它已声明组件已启动。
- 全部组件启动且各自 healthcheck 通过 → `success`，写入 `running-project.json`（URL + 组件状态）。
- `partial` / `failed-runtime` 仍写日志与每组件状态，不写可供 explore 的 `RunningProject`。
- `stop(project)` 只拆除本工具启动的组件（依据 `running-project.json`）。stop 之后这些进程必须消失。
- `Discovery.scan()` 与 start 独立：start 失败仍可调用 scan 占位。不实现真实 explore / execute。
- 密钥保持 `secret_ref`。Agent 凭据不得进入目标应用环境。
- Linux；compose 与常见脚本在范围内。desktop / RN / iOS / Android / game 槽位仍未实现。

## 范围外（禁止在 M3 实现）

- Discovery explore / execute，或真实 LLM Agent
- Effect DAG / platform / Broker
- 克隆 `https://github.com/RocketChat/Rocket.Chat` 或任何真实产品仓库
- 声称可安全执行未信任的任意仓库

## 启动结果

只有每个已声明组件都启动且自己的 healthcheck 通过，才是 `success`。  
故意弄坏某一个组件的 install、顺序或 healthcheck，必须在结果中点名该组件。
